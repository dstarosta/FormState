Getting Started

FormState Guide

Schema-derived form state for React 19. No registration, no wrappers, no magic — the data lives in the schema, and your inputs are just inputs.

FormState pairs with Zod Mini to make a single schema the source of truth for field types, validation, constraints, metadata, and identity. State is a plain object you read directly. Updates produce new references that flow through React's normal render cycle, so useEffect, useMemo, and the React Compiler work the way the syntax suggests. There is nothing to register and no wrapper to render through.

Key traits:

  • Schema-first — one Zod schema drives types, validation, constraints, and metadata. Form data is the schema instantiated, not a separate registry.
  • Path expressions — address nested and array fields with typed lambda paths: (path) => path.info.address. Refactor-safe, IDE-navigable, no string keys.
  • End-to-end type safety — generics flow from schema to every method signature, callback, and state accessor.
  • Pure React, no magic — you call change, you read formState.data, React re-renders normally. No register() spreading hidden props, no ref-mediated value tracking, no render props.
  • React 19 ready — works with server actions, useFormStatus, useOptimistic, Suspense, and the new action prop on <form>.
  • Official ESLint plugin — schema-derived state has a narrow, well-defined misuse surface, which makes static linting unusually effective. The plugin catches footguns the runtime can't — like passing a useWatch return value into a hook dependency array — at development time.
  • Zero-config defaults — validation on change, errors after touch, submit flow all work out of the box.

Installation

Requirements

FormState requires React 19.2 or greater, Zod 4.x and TypeScript 5.9 or greater.

Install FormState — Zod v4 is bundled as a peer dependency. NPM 7+ installs it automatically, PNPM does not.

bash
npm install react react-dom zod
npm install github:dstarosta/FormState#v1.0.0

Then import from the package root:

typescript
import { useFormState, z } from 'form-state';
Important

z should be imported from 'form-state', not 'zod' or 'zod/mini'.

ESLint

FormState ships an official ESLint plugin that catches common mistakes at development time — incorrect schema primitives, useWatch return values as hook dependencies, unsafe password inputs, unstable debounced callbacks, and groups placed on nested schema properties.

The plugin requires ESLint 9.0 or greater, which introduced flat config as the default format.

The only available config is recommended. It enables all the rules.

Configuration (flat config only)

javascript
// eslint.config.js
import { defineConfig } from 'eslint/config';
import formStatePlugin from 'form-state/eslint';

export default defineConfig([
  {
    extends: [
      // ... your other configs
      formStatePlugin.configs.recommended,
    ],
    rules: {},
  },
]);

Rule severities can be overridden individually via rules:

javascript
rules: {
  'form-state/avoid-input-password': 'error',
}

Rules

Rule Description Default Fixable
avoid-input-password Enforces using <SecureInput> instead of <input type="password"> inside forms with an action or onSubmit handler. Plain password inputs expose the value in the DOM, in DevTools, and to browser extension scanners. warn ✅
no-inline-schema Disallows constructing a schema inline as the first argument to useFormState() or useFormStateContext(). An inline schema is rebuilt on every render and invalidates the hook's subscriptions — hoist the schema to module scope or memoize it. error
no-nested-group Disallows group() on nested schema properties. Groups are only allowed on root-level properties, so a group placed on an object field, an array element, or any deeper field is reported instead of failing at runtime. error
no-watch-dependency Prevents using useWatch() return values as hook dependencies. useWatch values change via external store subscriptions and are not synchronized to React state — they must not appear in dependency arrays. error
stable-debounced-callback Enforces stable callback references in change() calls that set debounceIntervalMs. An inline function resets the debounce timer on every render, preventing the callback from ever firing. error
use-form-schema Enforces using FormState's formString(), formNumber(), formBoolean(), formDate(), and formArray() helpers instead of raw Zod primitives in form schemas. These helpers add the blank-value and optionality semantics HTML inputs require. warn ✅
Getting Started

Philosophy

FormState is built around a small set of ideas that inform every design decision. Understanding them makes the library predictable to use and straightforward to extend.

Built on patterns React developers already know

FormState doesn't invent its own vocabulary. Its building blocks map to patterns already in a working React developer's muscle memory — React 19 form actions used directly, Reselect-style memoized selectors, Immer-style immutable updates via updateState, clsx-style class composition through classNames and formClasses, and a Redux-style typed store mutated by actions and observed by listeners. Each pattern is documented in its own section below.

The deliberate constraint is to keep magic to a minimum. No register() spreading hidden props onto inputs, no ref-mediated value tracking, no implicit re-render orchestration, and — most importantly — no render prop wrapping every field. Inputs are plain HTML elements; the form's state is a plain object you read directly. When something works, it works because the rules are the same as the rest of React — not because the library quietly intervened on your behalf.

Depth over portability

Form libraries that target every UI framework and every schema library can only ship what those targets have in common. Framework-agnostic cores can't lean on React 19's form actions, useFormStatus, useOptimistic, Suspense for pending submissions, or Server Actions — those are host-specific. Schema-agnostic cores can't surface any one library's full validation surface either, because the adapter layer between them collapses everything to a common interface.

FormState makes the opposite trade: a hard commitment to React 19+ and Zod v4 Mini, used at full depth. React 19 features are used directly, not paraphrased through an adapter. Zod's check chains, refinements, z.regexes, and inferred types flow through to the form layer without translation. The cost is real lock-in — swapping out React or the schema layer isn't a one-line adapter change, it's a refactor with bug risk. The trade is deliberate: FormState targets modern React developers who have already chosen React 19 and Zod 4, and rewards that choice with deeper integration than any portable library can offer.

TypeScript first

Types flow end-to-end from your schema through every method signature, callback, and component prop. There are no any casts, no silent type widening, and no generics to pass by hand — inference does the work.

Path expressions are type-checked at compile time. (path) => path.info.age is valid or it isn't, and the error lands on your input's prop — not inside a render-prop wrapper two levels up. After a successful submit, state.data is fully narrowed: string, not string | ''.

See the TypeScript section for the full exported type reference and tsconfig requirements.

Built for React 19

FormState is built around React 19's form model, not bolted on top of it. The Form component returned by the hook accepts an async action prop directly — no onSubmit wiring, no e.preventDefault(). Because it uses a real <form action>, React 19's useFormStatus works in any child component without any extra setup, and server actions drop in without adapters. This deep integration means:

  • The browser's native form submission behavior is fully preserved. See Form Submission, Next.js, React Router 7 and TanStack Start.
  • Server Actions drop in seamlessly with no adapters or wrappers required. See Next.js, React Router 7 and TanStack Start.
  • FormData is natively supported along with JSON data. See Form Submission.
  • Suspense support allows you to declaratively handle loading states for pending submissions. See TanStack Query.
  • ErrorBoundary works out of the box to gracefully catch and display submission errors. See TanStack Query.
  • useFormStatus works in any child component without extra setup or context providers.
  • useOptimistic integrates naturally for instant UI feedback during submissions.
  • startTransition is fully supported — render form components in the background without blocking the main thread.1
  • Predictable render cycle. Form state flows through React's normal render path — including for uncontrolled inputs — so every value is reactive and reference-stable. The one deliberate exception is useWatch, which bypasses React for high-frequency reads.2
  • Immutable form state supports built-in memoized selectors and standard React hooks like useEffect/useLayoutEffect, useMemo and useCallback.

  1. Libraries that are using useSyncExternalStore for form state management have problems with React concurrent rendering, specifically background transitions.

    React Form Hook: React v19 Discussion #11832
    Tanstack Store (powers Tanstack Form): useSyncExternalStore and React concurrent mode #262

  1. Because useWatch bypasses React's render cycle, its return value can change between renders without triggering React's normal dependency tracking. That's what makes it fast for high-frequency reads — but it also means the value must only be used inside the render function, never as a useEffect, useMemo, or useCallback dependency. The no-watch-dependency ESLint rule catches this statically.

Schema-driven, non-intrusive

One Zod schema is the single source of truth for field types, validation rules, error messages, allowed values, ranges, and human-readable labels. It lives outside your components — controls are plain HTML inputs that never import or reference the schema directly.

This keeps component signatures simple and the schema portable. You can reuse the same schema for server-side API validation, share it across multiple forms, or version it independently of your UI. The schema is expressive — cross-field rules, async validators, conditional requirements — but that complexity stays in one place rather than being distributed across input components.

React is controlled

Every field is controlled by default: formState.data is the source of truth and React renders from it. This makes the form fully predictable — any state transition is visible as a plain object diff, which means conditional logic, cross-field validation, and debugging are all just JavaScript.

Edge cases:

  1. Uncontrolled inputs are available as an escape hatch for high-frequency fields where re-rendering on every keystroke is undesirable. The value is read from the DOM at submit time and fires no intermediate state updates:

    tsx
    <input
  name="bio"
  defaultValue={formState.data.bio}
  onBlur={(e) => formActions.change('bio', e.target.value, { touch: true })}
/>

    To observe a raw typed value — a live character counter, a search preview — without triggering a full re-render, see useWatch.

  2. Resetting form state — clearing every field back to its initial values when the user switches to a new record — follows the same React idiom: change the key prop on the component that owns useFormState. This is Dan Abramov's reset state with a key pattern — the parent remounts, every hook inside it resets, and useFormState starts fresh from initialData.

    tsx
    function EditPage({ id, data }) {
  // Key the component that owns useFormState so the hook unmounts and starts fresh
  return <EntityForm key={id} data={data} />;
}

function EntityForm({ data }) {
  const { Form } = useFormState(schema, { initialData: data });
  return <Form>...</Form>;
}

    The hook has to live inside the keyed component. If useFormState sat in EditPage instead, state would persist across id changes because React keeps the parent's hook alive.

Immutable form state

Every formState update produces a new object reference — no in-place mutation, no shared mutable containers. This is what makes FormState safe for the full range of React patterns: useMemo, useEffect dependency arrays, React.memo, and the React Compiler all rely on reference equality to detect changes. Libraries that store form state in a mutable ref or an external store — including React Hook Form and TanStack Form — bypass React's change-detection entirely, which means those optimisations silently stop working for form-derived values.1

  1. Both libraries have open reactivity and reference-stability issues that surface in ordinary React patterns and especially under the React Compiler — direct consequences of holding form state outside React's render cycle.

    #2090 — form.Subscribe causes unnecessary re-renders when selector returns objects or arrays

State helpers

Three standalone helpers cover the cases where you need to read, create, or update form data without going through the formActions API on a live form instance.

The getState method reads form data outside the form's render tree — in components or utility modules that have only a plain data object and the underlying Zod schema, not the live formState.

tsx
import { getState } from 'form-state';

const address1Zip = getState(formSchema, data, (path) => path.addresses[0].zipCode);

The createState method is used to generate an object with an initial state outside of the form context.

tsx
import { createState } from 'form-state';

const data = createState(schema);

// Override some default property values with a partial initial state object.
const data = createState(schema, { name: 'John', info: { age: 24 } });

The updateState method is used to update partial state graphs and assign them back using the change method. The syntax is very similar to the produce method in the Immer library.

tsx
import { updateState } from 'form-state';

const updatedTags = updateState(data.tags, (draft) => {
  draft.push('Important'); // can be a complex array/object structure
});

formActions.change('tags', updatedTags);

The createSymbol method returns a fresh Symbol.for(uniqueId). Use it when manually constructing items for an array whose element schema declares a z.symbol() identity field — for example, seeding initial array data outside of createState or duplicating an existing item with a new identity.

tsx
import { createSymbol } from 'form-state';

// Duplicate an existing note with a fresh identity
const duplicated = {
  ...formState.data.notes[0],
  uniqueId: createSymbol(),
};

formActions.array.append((path) => path.notes, duplicated);

Also see Array Fields

No render props

TanStack Form, React Hook Form, and Formik all manage per-field subscriptions by wrapping each input in a special component or render prop. FormState takes a different approach: state lives in a plain object you read directly, and you wire inputs yourself with ordinary props. You can always build a layer of abstracted components on top — but you never have to.

tsx TanStack Form 
// Every field needs a render-prop wrapper
<form.Field name="name">
  {(field) => (
    <div>
      <input
        value={field.state.value}
        onChange={(e) =>
          field.handleChange(e.target.value)
        }
        onBlur={field.handleBlur}
      />
      {field.state.meta.errors.map((err) => (
        <span key={err}>{err}</span>
      ))}
    </div>
  )}
</form.Field>
tsx React Hook Form 
// Controlled inputs need a render-prop wrapper
<Controller
  name="name"
  control={control}
  render={({ field, fieldState }) => (
    <div>
      <input {...field} />
      {fieldState.error && (
        <span>
          {fieldState.error.message}
        </span>
      )}
    </div>
  )}
/>
tsx Formik 
// Field render prop to access per-field state
<Field name="name">
  {({ field, meta }) => (
    <div>
      <input {...field} />
      {meta.touched && meta.error && (
        <span>{meta.error}</span>
      )}
    </div>
  )}
</Field>
tsx FormState 
// No wrapper — read state and call actions directly
<div>
  <input
    value={formState.data.name}
    onChange={(e) => formActions.change('name', e.target.value)}
    onBlur={() => formActions.touch('name')}
  />
  {formState.touched.name && formState.errors.name && (
    <span>{formState.errors.name}</span>
  )}
</div>

There is no field object, no fieldState, no render prop argument. You work with the same formState and formActions everywhere. Passing data to a child component is a normal prop. Conditional fields are plain JSX. Moving a field into its own component means passing formState and formActions as props — no re-registration, no useController.

Trade-off

Render-prop wrappers exist to limit re-renders to the field level. FormState re-renders the component that called useFormState on every state change. For most forms this is imperceptible, but if you have hundreds of fields you can reduce churn by using uncontrolled inputs with defaultValue, useWatch to subscribe to individual fields, or debouncing change calls on high-frequency inputs.

TypeScript

FormState is built around a handful of exported generic state types that flow from your schema through every callback, accessor, and component prop. Understanding them unlocks the full type-safety story.

Requirements

FormState's types rely on features and inference improvements introduced in recent TypeScript releases. Two requirements apply to all projects using this library:

TypeScript version

Types require TypeScript 5.9 or greater. Earlier versions will produce incorrect or missing type errors.

Strict mode

Enable "strict": true in your tsconfig.json. Without it several key checks — including narrowing inside handleSubmit and discriminated-union narrowing on SubmitState — will not fire.

json
// tsconfig.json
{
  "compilerOptions": {
    "strict": true
  }
}

Type depth limitation

Path inference supports up to 10 levels of nesting. Beyond that the type resolves to an empty tuple and path inference stops working.

Tip

Keep schemas at 10 levels of nesting or fewer. If you find yourself hitting the limit, flatten repeated sub-structures into their own schemas and compose them at the top level rather than nesting further.

This is the same approach the React docs recommend for state shape — see Avoid deeply nested state.

Common Types

These helper types are exported from form-state for typing wrapper components, callbacks, and reusable helpers. The generic parameter T is your Zod schema type — the same one you pass to useFormState(schema, ...). Provide it explicitly when inference does not apply (for example, in the props of a generic component) so paths, errors, and state values stay typed end-to-end.

FormSchema in these examples

Throughout the examples below, FormSchema refers to your inferred schema type — type FormSchema = z.infer<typeof schema> — where schema is the object you pass to useFormState. Define it once and reuse it wherever a form type is needed.

FormPath<T>

The type of a path expression — either a top-level key string or an arrow function that navigates the form data tree. Use it when passing a field reference as a prop.

typescript
import { type FormPath } from 'form-state';

// A component that displays an error for any field
function FormError<T>({
  path,
  errors,
}: {
  path: FormPath<T>;
  errors: FormState<T>['errors'];
}) {
  const message = errors.get(path as (p: T) => unknown);
  return message ? <p className="error">{message}</p> : null;
}

// Caller — the compiler checks the path against FormSchema
<FormError path={(path: FormSchema) => path.info.age} errors={formState.errors} />

FormState<T>

The type of formState itself. Use it when writing callbacks that receive the state snapshot — e.g. debounce callbacks or change listeners.

Warning

The callback option requires a stable reference — define it outside the component or wrap it in useCallback.

typescript
import { type FormState } from 'form-state';

// Debounce callback — typed state snapshot
function NoteTextInput({
  index,
  callback,
}: {
  index: number;
  callback?: (state: FormState<FormSchema>) => void;
}) {
  const { formActions } = useSchemaFormState();

  return (
    <input
      onChange={(e) =>
        formActions.change((path) => path.notes[index].text, e.target.value, {
          debounceIntervalMs: 500,
          callback,           // fires after debounce with latest FormState
          touch: true,
        })
      }
    />
  );
}

FormMode

The union 'editable' | 'readOnly' | 'disabled'. Use it when building mode selector components.

typescript
import { type FormMode } from 'form-state';

type ModeSelectorProps = {
  mode: FormMode;
  onChange: (mode: FormMode) => void;
};

// The compiler rejects anything that is not a valid mode string
formActions.setMode('readOnly');   // ✅
formActions.setMode('published');  // ❌ Type error

SubmitState<T>

The discriminated union passed to your handleSubmit callback. Narrow on valid to get a typed data object.

typescript
import { type SubmitState } from 'form-state';

const onSubmit = async (state: SubmitState<FormSchema>, formData: FormData) => {
  if (!state.valid) {
    // state.errors is Record<string, string>
    // state.data is DeepPartial<FormSchema> — may have empty/invalid fields
    return state.errors;
  }

  // state.data is fully typed FormSchema here — no cast needed
  await api.save(state.data.name);   // string, not string | ''
  await api.save(state.data.age);    // number, not number | ''
  return true;
};

SubmitSuccessState<T>

Passed to the onSuccess callback — guaranteed valid data plus the raw FormData.

typescript
import { type SubmitSuccessState } from 'form-state';

function App() {
  const handleFormSubmit = ({ data, formData }: SubmitSuccessState<FormSchema>) => {
    // data is fully typed FormSchema
    const output = formData.get('output');
    if (output === 'redirect') {
      router.push('/done');
    } else {
      showDialog({ data, formData });
    }
  };

  return <AppForm onSubmitted={handleFormSubmit} />;
}

SchemaDataObject<T>

Produced by schema.toObject(data) or parseState(schema, obj, true).data — symbol fields stripped, empty strings removed, Date values serialized to strings via each field's configured format.

typescript
import { type SchemaDataObject } from 'form-state';

// Component that displays clean API-ready data
function JsonData({ data }: { data: SchemaDataObject<FormSchema> }) {
  return <pre>{JSON.stringify(data, null, 2)}</pre>;
}

// Usage
<JsonData data={schema.toObject(formState.data)} />

StateChangeListener<T>

The type for formHooks.useListener callbacks.

typescript
import { type StateChangeListener } from 'form-state';

// Defined outside the component
const listener: StateChangeListener<FormSchema> = ({ type, data, submitCount }) => {
  if (type === 'submit') {
    analytics.track('form_submit', { count: submitCount, name: data.name });
  }
};

// In the component
formHooks.useListener(listener);

Group<T, G>

The type returned by formState.getGroup(name) for the group G of schema T. Use it to type a component prop that receives a single group's slice of the form state — the bundle is narrowed to exactly the fields assigned to that group. The group name is checked against the schema, so an unknown name is a compile error.

typescript
import { type Group } from 'form-state';

// A section component that receives one group's bundle as a prop
function ContactSection({ contact }: { contact: Group<FormSchema, 'contact'> }) {
  return (
    <fieldset>
      <legend>Contact</legend>
      <input value={contact.data.email} readOnly />
      <input value={contact.data.phone} readOnly />
      {/* contact.data.age — compile error: 'age' is not in the 'contact' group */}
    </fieldset>
  );
}

// Caller — getGroup() returns a value assignable to the Group prop
<ContactSection contact={formState.getGroup('contact')} />

DeepPartial<T>

A recursive Partial — every property at every level of nesting becomes optional. The initialData option accepts DeepPartial<T>, so you can seed the form from an API response or a saved draft without providing every field.

typescript
import { type DeepPartial } from 'form-state';

const { data: draft } = useQuery<DeepPartial<FormSchema>>({
  queryKey: ['draft', draftId],
  queryFn:  () => api.getDraft(draftId),
});

// Pass it directly as initialData — no need to fill in every field
const { formState, formActions } = useFormState(schema, {
  initialData: draft,
});

Options Types

Every form action accepts an options object whose type is exported from form-state. Import these when typing wrapper components or helpers that forward action options. Types parameterized by T take your Zod schema type.

ElementFocusOptions<T>

Options for formActions.focus.

Field Default Description
errorKey — When provided, focuses only if there is an active error at the given field path or manual error key. Accepts a path expression or a string key.
focusVisible true Shows that the element is focused using an outline style, if defined.
preventScroll false Do not scroll the focused element into view.
selectText false Selects the text content of the focused input.

FormChangeArrayOptions<T>

Options for the formActions.array.* methods (append, insert, remove, move, swap, replace). Same shape as FormChangeOptions minus debounceIntervalMs.

Field Default Description
callback — Optional callback to run after the form state has been changed. Receives the updated FormState and FormStatus.
touch false Mark affected fields as touched.
validate true Validate the form after the array change. Overridable via the validateOnChange hook option.

FormChangeOptions<T>

Options for formActions.change.

Field Default Description
callback — Optional callback to run after the form state has been changed. Receives the updated FormState and FormStatus. Must be stable — define it at module scope or wrap it in useCallback.
debounceIntervalMs 0 Debounce interval in milliseconds before dispatching the change. Intended for text inputs paired with defaultValue — see Debounced Changes.
touch false Mark the field as touched.
validate true Validate the field after the change. Overridable via the validateOnChange hook option.

FormClassOptions

Options for formClasses(nameOrPath, options). Combine a custom CSS prefix with a classNames string or FormClassCallback. See CSS Classes for usage patterns.

Field Default Description
prefix 'form-state' Overrides the CSS prefix for the generated state classes ([prefix]__error, [prefix]__touched, [prefix]__required, [prefix]__disabled, [prefix]__readonly) for this call only. Set globally via the cssOptions.prefix option of useFormState. Set to null to disable prefix classes entirely.
classNames — Either a static string appended verbatim, or a FormClassCallback that receives { isError, isTouched, isRequired, mode } and returns a clsx-compatible value (string, object, array, or falsy).
Prefix classes

Prefix classes are emitted automatically based on the field's state and form mode — [prefix]__required, [prefix]__disabled, [prefix]__readonly, [prefix]__touched, and [prefix]__error. They sit at the front of the class string and are independent of classNames. Disable them with prefix: null. See CSS Classes for the full conditions.

FormClassState

The argument passed to a FormClassCallback.

Field Type Description
isError boolean true when the field has a validation error and the form has been validated.
isTouched boolean true when the field has been touched.
isRequired boolean true when the field is required by the schema.
mode FormMode Current form mode — 'editable', 'readOnly', or 'disabled'.

FormClassCallback

A callback that produces CSS classes from the current field state. Accepted by formClasses(field, ...) and by cssOptions.classNames. Receives a FormClassState ({ isError, isTouched, isRequired, mode }) and returns a clsx-compatible value. Import this type when defining the callback outside a component — e.g. to share styling across forms or to keep a stable reference across renders.

typescript
type FormClassCallback = (state: FormClassState) => FormClassValue;

type FormClassValue =
  | string
  | Record<string, boolean | null | undefined>
  | readonly FormClassValue[]
  | false
  | null
  | undefined;
typescript
import { type FormClassCallback } from 'form-state';

// Shared field styling — defined once, reused across forms.
const fieldClasses: FormClassCallback = ({ isError, isTouched, mode }) => [
  'block w-full rounded border px-3 py-2',
  mode === 'disabled' && 'bg-slate-100 text-slate-400 cursor-not-allowed',
  isError && isTouched && 'border-red-400 bg-red-50/50',
];

// Apply per call.
<input className={formClasses('name', fieldClasses)} />

// Or as the form-level default.
useFormState(schema, { cssOptions: { classNames: fieldClasses } });

FormInitOptions<T>

The second argument to useFormState(schema, options) — controls initial data, validation timing, and miscellaneous form-wide behavior.

Field Default Description
cssOptions { prefix: 'form-state' } Form-level defaults for formClasses — accepts the FormClassOptions fields (prefix and classNames). A per-call formClasses(field, ...) argument fully replaces the form-level value for the same key. Set cssOptions.prefix to null to opt out of the generated prefix classes (see CSS Classes).
debounceCacheCapacity 50 Capacity of the debounce callback cache used by change. A non-positive value disables debouncing. Smaller values save memory but can drop pending callbacks under heavy concurrent use.
errorMessageSeparator '|' Separator used when multiple errors are joined into one message for the same state property.
inferredNameFormat 'bracket' Default format used by inferName — 'bracket' produces info[address][city], 'dot' produces info.address.city.
initialData — DeepPartial object with property values applied on mount. Non-dirty fields stay in sync with reactive updates to this reference.
initialMode 'editable' Initial FormMode — one of 'editable', 'readOnly', or 'disabled'.

Schema-derived state, in plain terms

Most form libraries — TanStack Form, React Hook Form, Formik — let each field component own its value. When a <Field> mounts, it registers with the form. When it unmounts, it unregisters. The form's data at any given moment is whatever the currently-mounted fields say it is. Whether that registry lives in DOM refs (React Hook Form) or an external store (TanStack Form) is a detail — in both cases the data is a side-effect of which components are currently rendered.

FormState works the opposite way. The schema declares the form's shape up front, so the data exists before any field component renders. Fields are plain controlled inputs reading from and writing to a shared state object. Nothing registers, nothing unregisters. That single design choice rules out an entire class of mount-lifecycle bugs — these aren't bugs FormState has patched, they're bug classes the architecture rules out.

Component-Owned State: Concrete Bugs

Array field identity desyncs from state ✅ immutable operations, no generated IDs — use a Symbol field if item identity is needed ❓ safe if using built-in methods; direct mutation desyncs 🛑 useFieldArray tracks by generated ID; outside mutation desyncs

The same design choice has consequences that extend beyond the bug catalog:

  • State follows React's rules. data.firstName in a useEffect dependency works the way the syntax suggests. TanStack Form keeps state in TanStack Store, and Final Form in its own external store — reads like form.state.values.x look identical to React state but don't trigger re-renders or invalidate dependency arrays. Silent footgun, especially for developers still building their React mental model.

  • Validation is deterministic. TanStack Form's per-field validators register at mount and fire on their own event slots (onChange, onBlur, onSubmit) — which is why an empty submit can light up every error at once, and individual errors can flicker as you type depending on which slot ran last. FormState runs the whole schema once over the canonical state on every change, so the error list is a pure function of the data — same input, same errors, every time.

  • Footguns are caught at lint time. FormState ships an official ESLint plugin that flags misuse patterns the runtime can't catch — for example, passing a useWatch return value into a hook dependency array. No other form library ships an official equivalent: React Hook Form has only a community-maintained plugin; TanStack Form has none. The asymmetry isn't an accident — static linting works best when the library has a narrow, well-defined misuse surface, which schema-derived state happens to provide.

Form data as a state slice

Most form libraries treat the form as a self-contained island: data goes in via defaultValues, comes out via handleSubmit, and is opaque to the rest of the app in between. Reading the current value of a field elsewhere in the tree — for a sidebar preview, a dependent query, or to persist to local storage — forces lifting state up, drilling props, or reaching in with refs.

A consequence of component-owned state: the subscription APIs other libraries do expose (useWatch, form.subscribe) only fire inside React's render cycle. Wiring a non-React consumer — a Redux middleware, a service worker, a BroadcastChannel across tabs — means writing your own bridge and keeping it in sync as fields mount and unmount. FormState's state is a real store with a stable, schema-defined shape and a typed event stream, which is exactly the contract every "subscribe to changes" integration already expects.

FormState treats form data the way Redux treats application state: a typed, observable slice with a defined shape, accessed anywhere via context, mutated by actions, and subscribable by listeners. The schema is the slice's contract.

  • Context-based access to data, not just the API. Other libraries' context (useFormContext, formContext) exposes the form instance; you still subscribe per-field with watch or <Controller> to get reactive values. With FormState, wrap a tree with formConnect and any descendant calls useFormStateContext to read the form's data, status, and actions directly as a typed, subscribed slice — selector-style, so reads are reactive without forcing tree-wide re-renders.

  • Listeners sync to other stores. formHooks.useListener is FormState's equivalent of store.subscribe: mirror state into a Redux slice, push it into TanStack Query, write to IndexedDB, broadcast across tabs — anything with a "set" API can stay in lockstep with the form.

  • Lifecycle as a single tagged stream. Listeners receive a tagged event — 'change', 'submit', and so on — so the form's lifecycle becomes a substrate for features beyond validation: multi-step wizards that advance on each step's submit, undo/redo by snapshotting state on every change, draft persistence to sessionStorage that clears on successful submit. Other libraries route change and submit through separate APIs; FormState routes both through one ordered stream, so handling them stays in one place.

  • Replace-style updates for async data. formActions.replace(data) swaps in new data while preserving schema invariants — dirty tracking, validation, and derived state continue to work correctly across the swap.

  • Survives lazy mounts and Suspense. Because state is schema-derived, a lazy()-loaded or <Suspense>-wrapped field group can arrive at any time — the data was there before the component, and stays there if it unmounts.

Form state as data slice — examples:

// Mirror every valid form change into a Redux slice
formHooks.useListener((state) => {
  if (state.type === 'change' && state.valid) {
    dispatch(updateFormState(formSchema.toObject(state.data)));
  }
});

// Hydrate the form from a fetch — form status and schema invariants preserved
useFetchData((data) => {
  formActions.replace(data);
});

// Draft persistence — restore on mount, save on change, clear on successful submit
const savedData = sessionStorage.getItem('draft');

const form = useFormState(schema, {
  initialData: savedData ? JSON.parse(savedData) : undefined,
});

formHooks.useListener((state) => {
  if (state.type === 'change') {
    sessionStorage.setItem('draft', JSON.stringify(state.data));
  } else if (state.type === 'submit') {
    sessionStorage.removeItem('draft');
  }
});

Other form libraries treat cross-store integration as application-developer plumbing. FormState treats it as a first-class surface — the form isn't an island, it's a participating member of your state ecosystem.

When FormState is the wrong choice

FormState's design assumptions don't suit every project. The fit is best when these are true; if one or more isn't, another library is likely the better tool.

  • You aren't already using Zod. The schema isn't an optional resolver here — it's the contract that drives data shape, derived constraints, typed paths, and the async-validation pipeline. Adding Zod purely to use FormState pays Zod's bundle cost without recouping it elsewhere; React Hook Form with a lightweight validator (or none at all) will be smaller and simpler.

    Yup, Valibot, Joi, ArkType, and hand-rolled validators don't plug in. React Hook Form and TanStack Form are schema-agnostic and will integrate with what you already use.

  • You need minimum-bundle granular re-renders by default. FormState re-renders the calling component on every state change unless you opt in to useWatch or uncontrolled inputs. For a 100-field data-entry form where every keystroke matters, React Hook Form's register-by-default model requires less thinking to get there.

  • You expect form state and application state to be the same thing. FormState owns form-editing state — masked strings, empty-vs-undefined, dirty/touched, validation status — using its own internal store. Like React Query owning server-cache state alongside Zustand, FormState coexists with Redux, MobX, Zustand, or any external store.

    A one-line useListener mirrors every valid change into the external store via schema.toObject(). That call translates the "form" representation into the "API/business" representation, field by field:

    • empty formNumber, formBoolean, etc. → undefined — the form holds '', the type doesn't
    • empty formString → undefined, only with allowEmpty: false
    • formDate strings → Date objects
    • raw mask values → unmasked values

    In short: the form holds the editing shape, the external store holds the canonical shape, and the schema is the bridge between them. If instead you want a single store to hold both representations and drive the form directly — with no bridge — then FormState's schema-derived model isn't the right fit.

In short

None of the above is a flaw to apologize for — they're consequences of the bets the library makes. Forms that fit those bets get a meaningfully better developer experience than the generic libraries can provide. Forms that don't fit them are better served by picking a library whose bets line up with the constraints.

Core Concepts

Defining a Schema

Every form starts with a schema. FormState re-exports a z object that extends Zod Mini with form-aware field constructors. These constructors encode required, error messages, date formats, and allowed values directly into the schema so FormState can read them automatically.

typescript
import { z } from 'form-state';

const schema = z.strictObject({
  // Required string with custom error and extra validators
  name: z
    .formString(
      { required: true, error: 'Name is required' },
      z.regex(/^[\w\s'-]+$/, 'Name contains invalid characters'),
      z.maxLength(50, 'Name must be 50 characters or less')
    )
    .with(z.describe('Full Name')),

  // Optional number with range constraints
  age: z
    .formNumber(z.gte(0, 'Age must be positive'), z.lte(150, 'Age is out of range'))
    .with(z.describe('Age')),

  // Date with a specific display format
  birthDate: z
    .formDate(
      { dateFormat: 'MM/dd/yyyy' },
      z.gte(new Date(1900, 0, 1), 'Date too far in the past')
    )
    .with(z.describe('Birth Date')),

  // Enum — only these string literals are valid
  status: z.formValues(['active', 'inactive', 'pending']).with(z.describe('Status')),

  // Boolean without an empty string value
  isAdmin: z.formBoolean({ required: true }).with(z.describe('Admin')),

  // Array of strings with length limits
  tags: z.formArray(z.string(), { minLength: 0, maxLength: 10 }).with(z.describe('Tags')),
});

type Schema = z.infer<typeof schema>;
// {
//   name: string;
//   age: number | '';
//   birthDate: Date | '';
//   status: 'active' | 'inactive' | 'pending' | '';
//   isAdmin: boolean;
//   tags: string[];
// }

Cross-field validation

Add .check(z.validate(...)) to the top-level object to express constraints that span multiple fields.

typescript
const schema = z
  .strictObject({
    priority: z.formBoolean(),
    notes: z.formArray(
      z.object({ typeId: z.formNumber(), text: z.formString() })
    ),
  })
  .check(
    z.validate(
      (data) => data.priority || data.notes.every((note) => note.typeId !== 2),
      { path: 'priority', error: 'Priority must be set to allow priority notes.' }
    )
  );

Schema Methods

These are the methods z exports from form-state that have no direct Zod equivalent. Each one wraps a standard Zod schema with form-specific preprocessing, metadata, or validation behaviour. Call them at schema-definition time, not inside components.

z.formString(opts?, ...checks)

Returns a schema that accepts string | ''. An empty string represents a blank field. When required is true, an empty string is treated as invalid.

Option Type Default Description
required boolean false Makes an empty string invalid.
error string — Custom error message for required and type validation.
allowEmpty boolean true Whether toObject() retains an empty string in the output. Set to false to strip blank fields from submitted data.
normalize 'NFC' |
'NFD' |
'NFKC' |
'NFKD' 		— Unicode normalization form to apply to the string before validation, equivalent to String.prototype.normalize(form). Omit to skip normalization.

Zod string checks — z.minLength, z.maxLength, z.regex, etc. — are passed as additional arguments after the options object.

typescript
// Optional string
z.formString()

// Required with custom error
z.formString({ required: true, error: 'Name is required' })

// Checks only — no options object needed
z.formString(z.maxLength(100, 'Too long'), z.regex(/^\w+$/, 'Letters only'))

// Required with options and checks
z.formString({ required: true, error: 'Required' }, z.maxLength(50))

// Strip empty strings from toObject() output
z.formString({ allowEmpty: false })

// Use built-in regex patterns from z.regexes instead of writing your own
z.formString({ required: true, error: 'Email is required' }, z.regex(z.regexes.email, 'Invalid email address'))
z.formString(z.regex(z.regexes.e164, 'Must be in international format, e.g. +12125551234'))

z.validate(predicate, params?)

Creates a Zod check for whole-object (cross-field) or single-field validation. Unlike z.refine, it runs on every validation pass by default — the optional condition parameter lets you gate it on the current set of prior errors. Pass the returned check to .check() on a z.object() or z.strictObject().

It can also be used for arrays or fields to perform custom validation that cannot be performed with the standard Zod-based method.

Parameter Type Default Description
predicate (item, prevItem?, prevResult?) => boolean — Returns true when the value is valid. prevItem and prevResult hold the input and result from the previous call (both undefined on first call); return prevResult to skip recomputation when relevant fields haven't changed.
condition (errors: ZodValidationError[]) => boolean always runs Called with the current validation errors before running the predicate. Return false to skip this check entirely.
path PropertyKey | PropertyKey[] — Key in formState.errors where the error is stored. Defaults to the root (no path).
error string — Custom error message.
typescript
// Shorthand — second argument is the error string
z.validate(
  (data) => data.endDate > data.startDate,
  'End date must be after start date'
)

// With path — error is stored under 'endDate'
z.validate(
  (data) => !data.endDate || data.endDate > data.startDate,
  { path: 'endDate', error: 'End date must be after start date' }
)

// With condition — skips this check when 'startDate' already has an error
z.validate(
  (data) => data.endDate > data.startDate,
  {
    condition: (errors) => !errors.some((e) => e.pathNotation === 'startDate'),
    path: 'endDate',
    error: 'End date must be after start date',
  }
)

// Attach to an object schema
const schema = z
  .strictObject({ startDate: z.formDate(), endDate: z.formDate() })
  .check(
    z.validate(
      (data) => !data.endDate || !data.startDate || data.endDate > data.startDate,
      { path: 'endDate', error: 'End date must be after start date' }
    )
  );

// Skip a complex validation when no relevant fields were changed.
const schema = z
  .strictObject({
    id: z.formString(),
    firstName: z.formString(),
    lastName: z.formString(),
  })
  .check(
    z.validate(
      (data, prevData, prevResult) => {
        if (
          prevResult !== undefined &&
          data.firstName === prevData?.firstName &&
          data.lastName === prevData.lastName
        ) {
          return prevResult;
        }

        // an intentionally over-complicated validation here
        let count = 0;
        for (const char of data.lastName) {
          count++;
        }
        for (const char of data.lastName) {
          count++;
        }
        return count <= 30;
      },
      { path: 'lastName', error: 'Full name must be 30 characters or less.' }
    )
  );

z.validateAsync(predicate, params?)

Asynchronous counterpart to z.validate. The predicate returns a Promise<boolean>, making it suitable for checks that depend on network calls — uniqueness lookups, server-side eligibility, address verification, and similar. The parameter shape (condition, path, error) and shorthand string-error overload match z.validate exactly.

useFormState detects async checks in the schema and runs them automatically. While an async pass is in flight, formStatus.validating is true and formStatus.valid is null. Rapid keystrokes do not produce out-of-order errors — only the latest pass surfaces.

Parameter Type Default Description
predicate (item) => Promise<boolean> — Resolves to true when the value is valid. To skip re-running the predicate when the input hasn't changed, use the skipWhen option below.
condition (errors: ZodValidationError[]) => boolean always runs Called with the current validation errors before running the predicate. Return false to skip this check entirely.
skipWhen (item, prevItem) => boolean deep equality Skip the network call when the value hasn't meaningfully changed since the last pass. By default the predicate is skipped when the inputs are deeply equal — override when the check is attached to a larger object but only depends on a few fields, e.g. (a, b) => a.sku === b?.sku && a.quantity === b?.quantity on an order schema where only sku and quantity affect the stock lookup.
submitOnly boolean false Run the check only on submit (or when you call formActions.validateAsync()). Useful for expensive verifications like payment authorization that don't need to fire on every keystroke.
path PropertyKey | PropertyKey[] — Key in formState.errors where the error is stored. Defaults to the root (no path).
error string — Custom error message.
debounceMs number 0 (disabled) When greater than 0, the predicate is debounced by this many milliseconds so it runs only once per quiet window, after the last call.
typescript
// Field-level async check — verify the username is not already taken.
// The default `skipWhen` (deep equality) automatically suppresses the
// network call when the input hasn't changed since the last committed pass.
const schema = z.object({
  username: z
    .formString({ required: true, error: 'Username is required' })
    .check(
      z.validateAsync(async (name) => {
        const res = await fetch(`/api/usernames/${encodeURIComponent(name)}`);
        const { available } = await res.json();
        return available;
      }, 'Username is already taken')
    ),
});

// Object-level async check with a condition gate and a custom skipWhen.
// Only the `sku` and `quantity` fields matter for the stock lookup, so the
// custom comparator ignores any other root-level changes.
const orderSchema = z
  .strictObject({
    sku: z.formString({ required: true }),
    quantity: z.formNumber({ required: true }),
    notes: z.formString(),
  })
  .check(
    z.validateAsync(
      async (order) => {
        const res = await fetch(`/api/stock?sku=${order.sku}&qty=${order.quantity}`);
        return res.ok;
      },
      {
        // Skip the network call until both fields parse cleanly.
        condition: (errors) => errors.length === 0,
        skipWhen: (a, b) =>
          b !== undefined && a.sku === b.sku && a.quantity === b.quantity,
        path: 'quantity',
        error: 'Not enough stock for the selected quantity',
      }
    )
  );

// Debounced async check — collapses keystroke bursts to a single network call
const usernameSchema = z.object({
  username: z
    .formString({ required: true })
    .check(
      z.validateAsync(
        async (name) => {
          const res = await fetch(`/api/usernames/${encodeURIComponent(name)}`);
          const { available } = await res.json();
          return available;
        },
        {
          path: 'username',
          error: 'Username is already taken',
          // Wait 400ms of inactivity before hitting the server.
          debounceMs: 400,
        }
      )
    ),
});

// Submit-only async check — the payment-method authorization is expensive
// and only meaningful right before submission. It is skipped on every
// change-driven validation and runs once when `formActions.validateAsync()`
// (or the submit flow) fires.
const paymentSchema = z.object({
  cardToken: z
    .formString({ required: true })
    .check(
      z.validateAsync(
        async (token) => {
          const res = await fetch(`/api/payments/authorize?token=${token}`);
          return res.ok;
        },
        {
          error: 'Card could not be authorized',
          submitOnly: true,
        }
      )
    ),
});
Tip

Use formStatus.validating to render a spinner next to the submit button or disable it while async checks are pending. For per-field indicators, subscribe to the async listener events (asyncValidating / asyncValidated) — they carry the triggerField path and are coalesced across overlapping passes so indicators don't flicker.

Predicate rejection

If the predicate's Promise rejects (network failure, bug in the validator), the rejection is surfaced as a root-level error (formState.errors['']) and formStatus.validating flips back to false so the form does not freeze. The error message is the Error.message of the rejection, falling back to 'Async validation failed.'.

Known caveat: on initial mount, useFormState probes the schema once via a synchronous parse to decide whether it needs the async pipeline. That probe invokes the predicate and abandons the returned Promise as soon as Zod detects it is async — so a predicate that rejects (rather than resolves false) will produce one unhandledRejection warning in development. The error is still surfaced correctly via the async pass that runs immediately after. Prefer resolving true / false over throwing in predicates; reserve rejection for unrecoverable failures.

z.someItem(predicate, error?)

Creates a Zod check that passes when at least one array element satisfies the predicate — equivalent to Array.prototype.some. Use with .check() on an array schema.

typescript
const schema = z.strictObject({
  participants: z.formArray(
    z.object({ role: z.formValues(['owner', 'member']), name: z.formString() })
  ).check(
    z.someItem(
      (item) => item.role === 'owner',
      'At least one participant must be an owner'
    )
  ),
});

z.everyItem(predicate, error?)

Creates a Zod check that passes when all array elements satisfy the predicate — equivalent to Array.prototype.every. Use with .check() on an array schema.

typescript
const schema = z.strictObject({
  prices: z.formArray(z.formNumber()).check(
    z.everyItem((price) => price === '' || price > 0, 'All prices must be positive')
  ),
});

z.uniqueItems(deepEquality?, params?)

Creates a Zod check that ensures all array items are unique. The error is placed at the path of the first duplicate element, making it easy to highlight the offending item in the UI. Use with .check() on an array schema.

Parameter Type Default Description
deepEquality boolean false Use deep equality instead of reference equality (===).
mapFn (item: T, index: number) => unknown — Map each item to a comparison value before checking uniqueness. Use to compare a specific property rather than the whole object.
error string — Custom error message placed on the duplicate element.
elementPath PropertyKey[] — Path within each array element where the error is attached. E.g. ['email'] makes the error appear under items[1].email.
ignoreValues unknown[] — Values skipped when checking for duplicates — typically [''] to ignore blank entries.
typescript
// Unique primitive strings — ignore blanks
z.formArray(z.formString()).check(
  z.uniqueItems(false, { error: 'Duplicate tag', ignoreValues: [''] })
)

// Unique by a property — error appears at the duplicate item's 'email' field
z.formArray(z.object({ email: z.formString(), name: z.formString() })).check(
  z.uniqueItems(false, {
    mapFn: (item) => item.email,
    elementPath: ['email'],
    error: 'Email must be unique',
    ignoreValues: [''],
  })
)

// Deep equality for object items
z.formArray(z.object({ x: z.formNumber(), y: z.formNumber() })).check(
  z.uniqueItems(true, { error: 'Duplicate coordinate' })
)

Missing Zod functionality

Any Zod feature not directly re-exported by form-state is available under z.advanced. This includes types such as z.advanced.union, z.advanced.nullable, z.advanced.transform, and others.

Warning

Methods under z.advanced are not guaranteed to be compatible with FormState. They bypass the form-aware preprocessing layer, so features like required validation, empty-string handling, and field metadata may not work as expected.

Core Concepts

Basic Usage

Call useFormState(schema, options) in your component and destructure what you need. The Form component returned by the hook is a pre-wired <form> element — use it in place of a plain <form>.

tsx
import { useFormState, z, convert } from 'form-state';

const STATUS_VALUES = ['active', 'inactive', 'pending'] as const;

const schema = z.strictObject({
  name: z.formString({ required: true, error: 'Name is required' }).with(z.describe('Name')),
  email: z.formString().with(z.describe('Email')),
  status: z.formValues(STATUS_VALUES).with(z.describe('Status')),
  isAdmin: z.formBoolean({ required: true }).with(z.describe('Admin')),
}).with(z.describe('Profile'));

export function ProfileForm() {
  const {
    formState,
    formStatus,
    formActions,
    formHandlers,
    formHooks,
    Form,
  } = useFormState(schema, {
    initialData: { name: 'Alice' },
  });

  const handleSubmit = formHandlers.handleSubmit(async (submitState) => {
    if (!submitState.valid) return submitState.errors;
    await saveProfile(submitState.data);
    return true;
  });

  return (
    <Form action={handleSubmit}>
      <h2>{formState.descriptions['']}</h2> {/* 'Profile' */}

      <label>
        {formState.descriptions.name}
        <input
          type="text"
          value={formState.data.name}
          onChange={(e) => formActions.change('name', e.target.value)}
          onBlur={() => formActions.touch('name')}
        />
        {formState.errors.name && <span>{formState.errors.name}</span>}
      </label>

      <label>
        {formState.descriptions.email}
        <input
          type="email"
          value={formState.data.email}
          onChange={(e) => formActions.change('email', e.target.value)}
        />
      </label>

      <label>
        {formState.descriptions.status}
        <select
          value={formState.data.status}
          onChange={(e) =>
            formActions.change('status', convert.toLiteral(e.target.value, STATUS_VALUES))
          }
          onBlur={() => formActions.touch('status')}
        >
          <option value="">Select status…</option>
          <option value="active">Active</option>
          <option value="inactive">Inactive</option>
          <option value="pending">Pending</option>
        </select>
        {formState.errors.status && <span>{formState.errors.status}</span>}
      </label>

      {/* Radio buttons — alternative rendering of the same field */}
      <fieldset onBlur={() => formActions.touch('status')}>
        <legend>{formState.descriptions.status}</legend>
        {STATUS_VALUES.map((status) => (
          <label key={status}>
            <input
              type="radio"
              value={status}
              checked={formState.data.status === status}
              onChange={(e) =>
                formActions.change('status', convert.toLiteral(e.target.value, STATUS_VALUES))
              }
            />
            {status}
          </label>
        ))}
        {formState.errors.status && <span>{formState.errors.status}</span>}
      </fieldset>

      <label>
        <input
          type="checkbox"
          checked={formState.data.isAdmin}
          onChange={(e) => formActions.change('isAdmin', e.target.checked)}
        />
        {formState.descriptions.isAdmin}
      </label>

      <button type="submit" disabled={formStatus.submitting}>
        {formStatus.submitting ? 'Saving…' : 'Save'}
      </button>
    </Form>
  );
}
Core Concepts

Path Expressions

Every method that accepts a field reference supports two equivalent syntaxes: a string key for top-level fields, and an arrow function path for anything nested or inside an array. The arrow function form is type-checked end-to-end — the TypeScript compiler rejects paths that don't exist in the schema.

typescript String — top-level only 
// Works for flat fields
formActions.change('name', value);
formActions.touch('name');
formState.errors.name;
formState.touched.name;
formState.dirty.name;
formState.required.name;
formState.descriptions.name;

// Arrays at the top level
formActions.array.append('tags', ['react']);
formActions.array.remove('tags', 0);
typescript Arrow function — any depth 
// Nested objects
formActions.change((path) => path.auto.modelId, value);
formActions.touch((path) => path.info.address.city);
formState.errors.get((path) => path.info.age);
formState.touched.get((path) => path.info.age);
formState.dirty.get((path) => path.info.age);

// Array items and their fields
formActions.change((path) => path.notes[index].text, value);
formActions.array.append((path) => path.profile.skills, ['TS']);
formState.descriptions.get((path) => path.notes[0].typeId);

Why arrow functions catch errors at compile time

The path lambda receives a typed proxy of your schema's data shape. The TypeScript compiler resolves the return type of the lambda and infers the correct value type for change, the correct error shape for errors.get, etc.

typescript
const schema = z.strictObject({
  user: z.object({
    age: z.formNumber(),
    name: z.formString(),
  }),
});

const { formActions, formState } = useFormState(schema);

// ✅ Correct — TypeScript knows 'age' accepts number | ''
formActions.change((path) => path.user.age, 30);

// ✅ Correct — TypeScript knows 'name' accepts string
formActions.change((path) => path.user.name, 'Alice');

// ❌ Type error — 'user.age' is number | '', not string
formActions.change((path) => path.user.age, 'hello');

// ❌ Type error — 'user.typo' does not exist on the schema
formActions.change((path) => path.user.typo, 'value');

Choosing between the two forms

Situation Use
Top-level field in a simple form Either — string is slightly shorter
Nested object (path.info.age) Arrow function
Array item field (path.notes[index].text) Arrow function
Passing path as a prop (FormPath<T>) Arrow function
Building the path dynamically at runtime String (arrow function can't be dynamic)

Form State

formState is the read-only snapshot of your form. Every property is keyed by field name and supports an optional path expression for nested access.

data

Current field values, typed from your schema.

typescript
formState.data.name              // string
formState.data.age               // number | ''
formState.data.info.address.city // string (nested)
formState.data.tags              // string[]
formState.data.tags[0]           // string

errors

Validation error messages, one per failing field.

typescript
// Top-level field — direct property access
formState.errors.name                              // 'Name is required' | undefined

// Nested field — use .get() with a path expression
formState.errors.get((path) => path.info.age)           // string | undefined
formState.errors.get((path) => path.notes[index].text)  // string | undefined

// Manual errors set via setError()
formState.errors.getManual('serverError')

// All current errors
formState.errors.getAll()    // string[]  — all messages
formState.errors.getKeys()   // string[]  — e.g. ['name', 'info.age']

When a field fails multiple checks, messages are joined with the errorMessageSeparator option (default |).

dirty / touched / required

Each is a boolean map with the same accessor pattern:

typescript
// Direct access for top-level fields
formState.dirty.name            // true after first change
formState.touched.name          // true after blur / explicit touch call
formState.required.name         // derived from schema — never changes

// .get() for nested fields
formState.dirty.get((path) => path.info.address.city)
formState.touched.get((path) => path.notes[index].text)
formState.required.get((path) => path.info.age)

// Enumerate all keys that are currently truthy
formState.dirty.getKeys()       // ['name', 'info.age', ...]
formState.touched.getKeys()

ranges

Min / max constraints extracted from the schema — ready to pass straight into HTML input attributes.

tsx
// Get the full range object
const ageRange = formState.ranges.get((path) => path.age);
// { type: 'range', format: 'integer', min: 0, max: 150 }

// Direct min/max helpers accept both forms
formState.ranges.getMin('age')              // 0
formState.ranges.getMax((path) => path.age)      // 150
formState.ranges.getMax('name')             // 50  (string maxLength)

// Wire directly to input attributes
<input
  type="number"
  min={formState.ranges.getMin((path) => path.age)}
  max={formState.ranges.getMax((path) => path.age)}
/>
<input
  type="text"
  maxLength={formState.ranges.getMax('name')}
/>

descriptions & patterns

tsx
// z.describe() values are available at runtime
formState.descriptions.name                         // 'Full Name'
formState.descriptions.get((path) => path.info.age) // 'Age'
formState.descriptions.get((path) => path.notes[0]) // 'Note'  (index normalised to [0])

// Patterns (from z.regex(), or z.formDate()) as raw strings for input[pattern]
formState.patterns.name                             // '^[\\w\\s\'-]+$'
formState.patterns.get((path) => path.info.id)      // '^\d+(-\d+)?$'
formState.patterns.get((path) => path.birthDate)    // 'yyyy-MM-dd'

// Use in JSX
<label>{formState.descriptions.get((path) => path.auto.modelId)}</label>

Preparing data for an API

schema.toObject(data) strips symbol fields (like z.symbol()) and removes optional fields whose value is an empty string, producing a clean object to send to your backend.

typescript
const payload = schema.toObject(formState.data);
// uuid symbols stripped, optional empty strings omitted
await api.post('/users', payload);

Date values are converted to strings using each field's configured format metadata (defaulting to "yyyy-MM-dd"). This applies to top-level dates, nested dates inside objects, and date elements inside arrays. Send the output straight to JSON-based APIs without an extra serialization pass.

typescript
const schema = z.object({
  birthDate: z.formDate(z.date(), { format: 'MM-dd-yyyy' }),
  registeredOn: z.formDate(z.date(), { format: 'MM/dd/yyyy' }),
  updateDates: z.formArray(z.formDate(z.date())), // default 'yyyy-MM-dd'
});

schema.toObject(formState.data);
// {
//   birthDate: '12-31-2020',
//   registeredOn: '06/30/2020',
//   updateDates: ['2019-12-12', '2020-04-15'],
// }

Schema Metadata

FormState extracts metadata from your schema at initialization time and exposes it as plain, typed objects — no extra wiring needed. All five live on formState and are keyed the same way as data and errors:

descriptions .with(z.describe('…')) Drive <label> text from a single source of truth

/>
Note

When a string field has multiple z.regex() checks, only the first one is stored in patterns. The title attribute is a good place to describe the full constraint in plain language.

touched

formState.touched tracks whether a user has interacted with a field. Its primary job is to gate error display — you almost always want to show an error only after a field has been touched, not the moment the form mounts.

tsx
// Read — top-level and nested
formState.touched.name                           // boolean
formState.touched.get((path) => path.info.age)        // boolean

// Typical pattern: show error only after interaction
{formState.touched.name && formState.errors.name && (
  <span role="alert">{formState.errors.name}</span>
)}

// Set on blur (most common)
<input onBlur={() => formActions.touch('name')} />

// Set immediately on change — good for selects and checkboxes
formActions.change((path) => path.category, value, { touch: true });

// Touch a field programmatically without changing its value
formActions.touch('name');
formActions.touch((path) => path.notes[index].text);

// Touch without running validation (validation runs by default)
formActions.touch('name', { validate: false });

// Inspect which fields have been touched
formState.touched.getKeys()                      // ['name', 'info.age', ...]
formStatus.touched                               // true if any field is touched
Tip

When editing existing data, pass initialTouched to pre-touch fields so errors are visible immediately without the user having to visit each field first.

Putting it all together — a fully wired field component

Combining descriptions, ranges, required, and patterns into a reusable component shows how much schema-driven metadata FormState gives you for free:

tsx
function TextField({ name }: { name: keyof FormSchema }) {
  const { formState, formActions, formClasses } = useSchemaFormState();

  const label     = formState.descriptions[name];
  const value     = formState.data[name] as string;
  const error     = formState.errors[name];
  const touched   = formState.touched[name];
  const maxLength = formState.ranges.getMax(name);
  const minLength = formState.ranges.getMin(name);
  const pattern   = formState.patterns[name];
  const required  = formState.required[name];

  return (
    <div className={formClasses(name)}>
      <label htmlFor={name}>
        {label}
        {required && <span aria-hidden> *</span>}
      </label>
      <input
        id={name}
        type="text"
        value={value}
        minLength={minLength}
        maxLength={maxLength}
        pattern={pattern}
        required={required}
        aria-invalid={touched && Boolean(error)}
        aria-describedby={error ? `${name}-error` : undefined}
        onChange={(e) => formActions.change(name, e.target.value)}
        onBlur={() => formActions.touch(name)}
      />
      {touched && error && (
        <span id={`${name}-error`} role="alert">{error}</span>
      )}
      {maxLength && (
        <small>{value.length} / {maxLength}</small>
      )}
    </div>
  );
}
Tip

For date fields, ranges.getMin and ranges.getMax return Date objects. Use formatDate(date, 'yyyy-MM-dd') to convert them to strings suitable for input[type=date].

Core Concepts

Form Groups

Larger forms are often organized into sections — contact details, shipping address, preferences. Form groups let you label related fields in the schema and then pull everything about that section out of the form state in one call.

Wrap a field with z.group(schema, name) to assign it to a group. Groups are only allowed on top-level fields:

tsx
const schema = z.object({
  email: z.group(z.formString({ required: true }), 'contact'),
  phone: z.group(z.formString(), 'contact'),
  street: z.group(z.formString({ required: true }), 'address'),
  city: z.group(z.formString({ required: true }), 'address'),
  newsletter: z.formBoolean(),
});

Call formState.getGroup(name) to get a bundle containing every form-state slice — data, errors, touched, dirty, required, ranges, patterns, and descriptions — narrowed to just that group's fields:

tsx
const contact = formState.getGroup('contact');

contact.data.email; // 'jane@example.com'
contact.errors.phone; // error message, if any
contact.required.email; // true

// Render a whole section from the bundle
<fieldset>
  <legend>Contact</legend>
  {Object.keys(contact.data).map((field) => (
    <div key={field}>
      <label htmlFor={field}>{contact.descriptions[field]}</label>
      <input
        type="text"
        id={field}
        value={contact.data[field]}
        onChange={(e) => formActions.change(field, e.target.value)}
        onBlur={() => formActions.touch(field)}
      />
      {contact.errors[field] && <span>{contact.errors[field]}</span>}
    </div>
  ))}
</fieldset>

Each bundle contains only the fields in that group — the address group never exposes email, and ungrouped fields such as newsletter appear in no group at all. The returned objects are read-only, just like the rest of the form state.

This also makes groups a natural fit for forms shown one section at a time, such as a multi-step wizard: render a single group per step while the rest of the form state stays intact in the background, then submit the whole form once every step is complete.

The group name is checked against the schema, so requesting a group that does not exist is a TypeScript error and autocomplete suggests the valid names.

Tip

Groups only apply to top-level fields. Placing a group on a nested object field or an array element is reported by the no-nested-group ESLint rule and throws when the form initializes.

Features

Validation

Validation runs automatically on every change and touch call by default. You control when errors surface to users through the touched pattern: only show an error once the field has been touched. Running validation on touch ensures empty required fields light up after a user tabs through them without typing.

Validation options

Option Default Description
validateOnMount false Run validation immediately when the hook mounts.
validateOnChange true Re-validate after every change call.
validateOnTouch true Run validation when a field is touched.
validateBeforeSubmit true Validate before treating a submit as successful.

Validating on demand

typescript
// Validate the full schema
formActions.validate();

// Validate and mark as submitted on success
formActions.validate({ submit: true });

// Validate with a custom async check (e.g. server-side uniqueness)
formActions.validate(
  async () => {
    const taken = await api.checkUsername(formState.data.username);
    return taken ? { username: 'Username is already taken' } : true;
  },
  { submit: true }
);

The custom validator receives no arguments — read formState.data directly. Return true for success or a Record<string, string> of field-key: error pairs to inject errors.

Auto-touch on error

When formActions.validate runs, every field that has an error — whether from the schema or from a manual error keyed to a real field — is automatically marked as touched. The same happens when formHandlers.handleSubmit encounters errors.

If your UI renders errors only for touched fields, every error becomes visible as soon as the user submits the form or runs full form validation.

Validating async schemas with validateAsync

If your schema contains async checks (for example, z.validateAsync for server-side uniqueness), use formActions.validateAsync instead of validate. It resolves to true when the form is valid and false otherwise.

typescript
const isValid = await formActions.validateAsync();

if (!isValid) {
  // Branch on isValid — formState.errors and formStatus.valid in this
  // closure are from the previous render and may not reflect the result.
  return;
}

validateAsync also works on sync schemas, so it's safe to use whenever you want to await a boolean result. For full form submission with an async schema, use formHandlers.handleSubmit — it already awaits validation before submitting the form.

Touching fields to reveal errors

Errors are computed on every change, but you typically only show them after the user has interacted with a field. Call touch on blur:

tsx
<input
  value={formState.data.email}
  onChange={(e) => formActions.change('email', e.target.value)}
  onBlur={() => formActions.touch('email')}
/>

{/* Only shown after blur */}
{formState.touched.email && formState.errors.email && (
  <p className="error">{formState.errors.email}</p>
)}

Or pass { touch: true } directly to change when you want to surface errors immediately (common for selects and checkboxes):

typescript
// Select / dropdown — touch immediately on pick
formActions.change((path) => path.auto.modelId, selectedId, { touch: true });

// Checkbox — touch and validate on click
formActions.change((path) => path.priority, e.target.checked, { touch: true });

// Radio buttons — top-level string form is fine here
formActions.change('sendEmail', 'yes', { touch: true });

Pre-touching fields

Mark fields as touched from the start — useful when editing existing data:

typescript
useFormState(schema, {
  initialData: existingRecord,
  initialTouched: ['name', 'email', (path) => path.info.age],
});
Features

Form Submission

formHandlers.handleSubmit(onSubmit, options?) returns an async action you pass to the Form's action prop. It validates the form, calls your handler with a typed SubmitState, and updates formStatus.submitted / formStatus.submitting automatically.

tsx
import { type SubmitState } from 'form-state';

const handleSubmit = formHandlers.handleSubmit(
  async (submitState: SubmitState<typeof schema>, formData: FormData) => {
    // Schema validation failed — return the error map
    if (!submitState.valid) {
      formActions.focusOnFirstError({ selectText: true });
      return submitState.errors;
    }

    // submitState.data is fully typed and validated here
    try {
      await fetch('/api/profile', {
        method: 'POST',
        headers: { 'Content-Type': 'application/json' },
        body: JSON.stringify(submitState.data),
      });
      return true; // success
    } catch (err) {
      // Surface a form-level error under any key you choose (here: serverError)
      return { serverError: 'Something went wrong. Please try again.' };
    }
  },
  {
    onSuccess: ({ data, formData }: SubmitSuccessState<typeof schema>) => {
      router.push('/dashboard');
    },
    onError: (state, status) => {
      formActions.focusOnFirstError();
    },
  }
);

return <Form action={handleSubmit}>...</Form>;

Focusing the first error

After a failed submission, jump the user to the first broken field:

typescript
formActions.focusOnFirstError({ selectText: true });

// Or focus a specific element
formActions.focus('email', { selectText: true });

// Focus only if the field has an error
formActions.focus('email', { errorKey: 'email' });

// Blur the currently focused element — useful to dismiss
// the on-screen keyboard on mobile after a successful submit,
// or to move focus out of the form before opening a modal.
formActions.blur();

Why use <Form> over a plain <form>

The Form component returned by the hook is a thin wrapper around <form> that wires several behaviours automatically. You can always drop down to a plain <form> — but you'll need to handle each of these yourself.

React 19 post-submit reset prevention 1 Includes <FormResetBlocker> automatically Must place <FormResetBlocker> inside the <form> manually
Native validation suppression Sets noValidate by default — browser popups never appear Must add noValidate manually or browser bubbles will show
Form data cache supression 2 Sets autoComplete="off" by default Must add autoComplete="off" manually or browser can cache form data that is inconsistent with the form state data.

  1. The autoComplete attribute/prop can still be set on individual input elements/components.

Using a plain <form> with onSubmit

If you prefer the traditional onSubmit pattern — or if you're integrating into an existing form element you don't control — use formActions.validate directly and wire reset and submit manually.

tsx
const { formState, formStatus, formActions, formHandlers } = useFormState(schema);

const handleSubmit = async (e: React.FormEvent<HTMLFormElement>) => {
  e.preventDefault();

  formActions.validate(
    async () => {
      // Optional: async cross-field or server-side check
      const taken = await api.checkEmail(formState.data.email);
      return taken ? { email: 'Email already registered' } : true;
    },
    {
      submit: true,
      callback: (state, status) => {
        if (status.valid) {
          api.save(schema.toObject(state.data));
        } else {
          formActions.focusOnFirstError({ selectText: true });
        }
      },
    }
  );
};

return (
  <form
    noValidate
    onSubmit={handleSubmit}
    onReset={formHandlers.handleReset}
  >
    <input
      value={formState.data.name}
      onChange={(e) => formActions.change('name', e.target.value)}
      onBlur={() => formActions.touch('name')}
    />
    {formState.errors.name && <span>{formState.errors.name}</span>}

    <button type="submit" disabled={formStatus.submitting}>Save</button>
    <button type="reset">Reset</button>
  </form>
);
Limitations

With a plain <form>, formHooks.useWatch will not work and SecureInput values will not appear in FormData. If you need either of those, use the Form component.

Working with FormData

The second argument to your handleSubmit callback — and the formData property on SubmitSuccessState — is the browser's native FormData built from the form elements at submission time. It contains every named field in the form, including entries that the Zod schema doesn't know about (hidden inputs, extra metadata fields).

Keys in FormData match the HTML name attributes on your inputs. For nested paths generated with inferName the key follows whichever notation was used — bracket by default:

typescript
// name="email"
//   formData.get('email')
// name={inferName(path => path.info.age)}
//   formData.get('info["age"]')
// name={inferName(path => path.tags[0], 'dot')}
//   formData.get('tags.0')

const onSubmit = async (state: SubmitState<FormSchema>, formData: FormData) => {
  if (!state.valid) return state.errors;

  // Raw string from FormData — useful for fields outside the schema
  const redirectTo = formData.get('redirectTo') as string | null;
  const age        = formData.get('info["age"]') as string | null;

  await api.save(state.data);
  return true;
};

Submitter tracking

When a form has multiple submit buttons with different name/value pairs, the browser is supposed to include the clicked button's value in FormData — but behaviour varies across browsers and async action forms. The Form component solves this by tracking event.submitter during the capture phase and patching FormData if the button's entry is missing.

tsx
// Two submit buttons with the same name but different values
<Form action={handleSubmit}>
  <button name="action" value="save">Save draft</button>
  <button name="action" value="publish">Publish</button>
</Form>

// In your handler — formData always carries the clicked button's value
const onSubmit = async (state: SubmitState<FormSchema>, formData: FormData) => {
  if (!state.valid) return state.errors;

  const action = formData.get('action'); // 'save' | 'publish'

  if (action === 'publish') {
    await api.publish(state.data);
  } else {
    await api.saveDraft(state.data);
  }
  return true;
};
Note

Submitter tracking only works with the Form component. A plain <form> relies on native browser behaviour, which may omit the button value in async action forms.

[prefix]__error Field has a validation error after the form has been validated. Suppressed in disabled mode.

The default prefix is 'form-state'. Setting it to null disables prefix classes entirely — no classes are generated automatically.

Initialize CSS options globally via cssOptions:

typescript
// Just the prefix.
useFormState(schema, { cssOptions: { prefix: 'my-form' } });

// Prefix plus a static `classNames` string applied to every field.
useFormState(schema, {
  cssOptions: {
    prefix: 'my-form',
    classNames: 'block w-full rounded border px-3 py-2',
  },
});

// Prefix plus a callback driving classes from the field state.
useFormState(schema, {
  cssOptions: {
    prefix: 'my-form',
    classNames: ({ isError, isTouched }) =>
      isError && isTouched ? 'border-red-400' : 'border-zinc-300',
  },
});

cssOptions accepts a prefix and a classNames value. Set them once and they apply to every formClasses(field) call. A per-call argument fully replaces the form-level value.

typescript
const { formClasses } = useFormState(schema, {
  cssOptions: {
    prefix: 'my-form',
    classNames: ({ isError }) => ['field', isError && 'field--invalid'],
  },
});

formClasses('name');
// "my-form__required my-form__error field field--invalid"

formClasses('name', ({ isError }) => isError && 'field--server-error');
// "my-form__required my-form__error field--server-error"
// The per-call callback fully replaces the form-level `classNames`.

Set cssOptions.prefix: null to disable prefix classes entirely. The callback still runs, so you can drive all styling from classNames alone. When the prefix is null, formActions.focusOnFirstError() falls back to locating the first errored field by its name attribute.

typescript
useFormState(schema, { cssOptions: { prefix: null } });

Adding custom classes

formClasses(field, ...) accepts four shapes for its second argument:

  • Omitted — emits the prefix classes only.
  • A string — appended verbatim, always applied.
  • A FormClassCallback — receives { isError, isTouched, isRequired, mode } and returns a clsx-compatible value: a string, an object (keys with truthy values are kept), an array (flattened recursively), or any falsy value (false, null, and undefined are filtered out).
  • A FormClassOptions object with prefix and/or classNames.
tsx
// 1) Static string — applied regardless of state.
<input className={formClasses('name', 'block w-full rounded border px-3 py-2')} />

// 2) Callback returning a string.
<input
  className={formClasses('name', ({ isError, isTouched }) =>
    isError && isTouched
      ? 'border-red-400 bg-red-50/50'
      : 'border-zinc-300 bg-white'
  )}
/>

// 3) Callback returning a clsx-style object.
<input
  className={formClasses('email', ({ isError, isTouched }) => ({
    'form-control': true,
    'is-invalid': isError && isTouched,
  }))}
/>

// 4) Callback returning an array (falsy entries are dropped).
<input
  className={formClasses('name', ({ isError, isTouched, mode }) => [
    'block w-full rounded border px-3 py-2',
    mode === 'disabled' && 'bg-slate-100 text-slate-400 cursor-not-allowed',
    mode === 'readOnly' && 'bg-slate-50 text-slate-600',
    isTouched && 'border-slate-400',
    isError && isTouched && 'ring-1 ring-red-500',
  ])}
/>

// 5) Options object — custom prefix plus a callback.
formClasses('name', {
  prefix: 'fld',
  classNames: ({ isError }) => ['field', isError && 'field--invalid'],
});
// e.g. "fld__required fld__error field field--invalid"

The utility classes in the snippets above (block, border-red-400, bg-slate-50, etc.) are Tailwind CSS classes, used purely for illustration. FormState has no opinion on the class names you return — substitute Bootstrap, your own CSS, or any other utility framework as appropriate.


Resolving class conflicts

FormState does not deduplicate or resolve conflicts between the classes you return. If two of your branches can produce conflicting classes for the same CSS property, gate them through mutually exclusive conditions in the callback — the ternary or object form above — so only one ever reaches the output.

Standalone classNames helper

classNames is the same clsx-style resolver that powers formClasses, exported for use outside of form fields. Pass it any number of FormClassValue arguments — each one a string, a clsx-compatible object, an array of either, or a falsy value — and it returns a space-separated class name string. Object keys with truthy values are kept; arrays are flattened recursively; false, null, and undefined are filtered out.

typescript
import { classNames } from 'form-state';

// String — returned as-is.
classNames('btn btn-primary');
// "btn btn-primary"

// Object — keys with truthy values are kept.
classNames({ 'btn': true, 'btn-primary': isPrimary, 'is-disabled': disabled });
// e.g. "btn btn-primary"

// Array — flattened recursively, falsy entries dropped.
classNames(['btn', isPrimary && 'btn-primary', { 'is-loading': loading }]);
// e.g. "btn btn-primary is-loading"

// Sequence — combine any mix of strings, objects, arrays, and falsy values.
classNames(
  'btn',
  isPrimary && 'btn-primary',
  { 'is-loading': loading, 'is-disabled': disabled },
  [size && `btn-${size}`, extraClass]
);
// e.g. "btn btn-primary is-loading btn-lg my-extra-class"

// Falsy input — returns an empty string.
classNames(null);
// ""

// No arguments — returns an empty string.
classNames();
// ""

Features

Input Controls

Drop-in input components that pair with useFormState for common value-shaping needs.

MaskedInput

MaskedInput restricts user input to a fixed pattern of slots and literal characters and always renders the full mask in place. Typing into a literal position jumps to the next slot; deleting a character clears the slot to its placeholder character (e.g. _) without shifting the rest of the input.

tsx
import { MaskedInput } from 'form-state';

<MaskedInput
  mask="(999) 999-9999"
  onChange={(event) => {
    formActions.change('phone', event.target.value);
    if (event.complete) {
      // Fires on the change that fills every required slot
    }
  }}
/>

Mask tokens

The mask prop is composed of tokens (slots that accept user input) and literal characters that are rendered as-is and skipped over while typing.

Token Accepts
9 A single digit (0–9)
a A single letter (A–Z, a–z)
* A single alphanumeric character
? Marks every following position as optional — they accept input but are not required for event.complete to flip to true. Useful for trailing extensions like (999) 999-9999? x99999.
any other character Treated as a literal — parentheses, dashes, slashes, dots, commas, colons, spaces, etc.

Customizing the placeholder

Slot positions display _ by default. Use the placeholder prop to override the character shown at unfilled slots — provide a string aligned with the rendered mask. Literal positions in the placeholder are ignored; the mask's literal always wins.

tsx
<MaskedInput mask="99/99/9999" placeholder="DD/MM/YYYY" />

For slot positions not covered by placeholder, set placeholderChar to '_' (default) or ' '. A space keeps the mask visually invisible until the user types into it, while still reserving the layout.

tsx
<MaskedInput mask="(999) 999-9999" placeholderChar=" " />

Input type and mobile keyboard

type is constrained to 'text' (default) or 'search' — types that respect the formatted mask string. Other native types like number or email would strip mask literals or apply conflicting validation, so they are intentionally not allowed.

inputMode is auto-detected from the mask: a digit-only mask (no a or * tokens) gets inputMode="numeric" so mobile users see the number pad without any extra config. Pass inputMode explicitly to override.

Value semantics

value, defaultValue, and onChange all use the formatted string with placeholder characters at unfilled slots — exactly what is rendered in the DOM. The one exception: when no slot has been filled, the value is the empty string (so a freshly-rendered field doesn't submit a placeholder template through FormData).

  • Empty: "" (browser shows the empty mask via the HTML placeholder)
  • Partial: "(555) 1__-____"
  • Complete: "(555) 123-4567"

Change and blur events

Both onChange and onBlur receive an event extended with two extra fields:

  • event.complete — true when every required mask slot is filled at the moment the event fires, otherwise false. Optional slots (declared with ?) do not need to be filled.
  • event.unmaskedValue — the user-entered characters concatenated in slot order, with literals and unfilled-slot placeholders stripped. Useful when you want to store or submit the raw digits/letters without the mask.
tsx
<MaskedInput
  mask="(999) 999-9999"
  onChange={(event) => {
    // event.target.value   = "(555) 123-4567"
    // event.unmaskedValue  = "5551234567"
    // event.complete       = true
  }}
  onBlur={(event) => {
    if (!event.complete) {
      formActions.touch('phone', { error: 'Please enter a full phone number' });
    }
  }}
/>

SecureInput

SecureInput is a drop-in password component that never stores the real value in the DOM. It shows bullets visually but passes the actual text only through controlled callbacks, preventing clipboard sniffing and browser auto-fill exfiltration.

tsx
import { SecureInput } from 'form-state';

<SecureInput
  type="password"
  onSecureChange={(value) => {
    // 'value' is the real plaintext — never touches the DOM
    formActions.change('password', value);
  }}
  onSecureBlur={(value) => {
    formActions.change('password', value, { touch: true });
  }}
/>

Features:

  • Displays masked bullets, real value stays in memory only.
  • Blocks copy, cut, paste, and drag to prevent leakage.
  • Ctrl+Z / Ctrl+Y undo protection.
  • Compatible with standard onChange for uncontrolled usage.

Debounced Changes

Pass debounceIntervalMs to change to delay downstream effects — useful for search inputs, async field validation, or expensive re-renders.

typescript
formActions.change('search', inputValue, {
  debounceIntervalMs: 400,
  callback: (state, status) => {
    // Fires 400ms after the last keystroke

  },

// Arrow function path — nested field
formActions.change((path) => path.notes[index].text, e.target.value, {
  debounceIntervalMs: 500,
  touch: true,
  callback: (state: FormState<FormSchema>) => {

Features

inferName

formActions.inferName generates the correct HTML name attribute value for a field, including nested paths. Use this when you need the browser's native FormData to carry the right keys — and when combining FormState with useWatch.

Two name formats

Nested paths can be serialised in two formats. The format you choose determines how the key appears in FormData when the form is submitted.

Format Path info.age Array item items[0].title Top-level name
'bracket' (default) info["age"] items[0]["title"] name
'dot' info.age items.0.title name

When you call formData.get(key) after submission, use the same format that was used for the name attribute. If you mix formats across fields, read each key with the matching notation.

tsx
// Bracket format (default) — infers: info["age"]
formActions.inferName((path) => path.info.age)

// Dot format — infers: info.age
formActions.inferName((path) => path.info.age, 'dot')

// Top-level string — always just the key itself
formActions.inferName('name')

// Uncontrolled input + useWatch combo
<input
  name={formActions.inferName((path) => path.id)}
  defaultValue={formState.data.id}
  onChange={(e) => formActions.change((path) => path.id, e.target.value)}
/>

// useWatch subscribes by the same name string
const watched = formHooks.useWatch(formActions.inferName((path) => path.id));

// Reading back from FormData on submit
const onSubmit = async (state: SubmitState<FormSchema>, formData: FormData) => {
  // bracket key (default format)
  formData.get('info["age"]');    // value of info.age
  // dot key
  formData.get('info.age');       // only if that field used 'dot' format
};

Change the default format for all fields globally:

tsx
const { Form, formActions } = useFormState(schema, {
  inferredNameFormat: 'dot', // all inferName calls default to dot notation

Memoized Selector (useSelector)

formHooks.useSelector is a hook that derives a memoized value from form state. Pass an array of input selectors and a result function — the result is only recomputed when one of the inputs changes by reference. The returned selector function is stable across renders and can be called with any state snapshot.

Simple selectors

A selector with a single input extracts or transforms one slice of state. The state type is inferred automatically from the schema — no manual annotation needed.

tsx
const { formState, formHooks } = useFormState(schema);

// Extract a field as-is
const selectName = formHooks.useSelector(state => state.name);

// Derive a boolean from a field
const selectIsAdult = formHooks.useSelector(
  state => state.age,
  age => typeof age === 'number' && age >= 18
);

selectName(formState.data)     // string
selectIsAdult(formState.data)  // boolean

Composable selectors

Any selector returned by useSelector can be used as an input to another useSelector call. Each step is independently memoized — a downstream selector only reruns when its upstream output actually changes.

tsx
// Filters the items array — reruns only when items changes
const selectActiveItems = formHooks.useSelector(
  state => state.items,
  items => items.filter(item => item.active)
);

// Counts the filtered list — reruns only when selectActiveItems output changes
const selectActiveCount = formHooks.useSelector(
  selectActiveItems,
  items => items.length
);

// Maps names — also reads from the already-filtered list
const selectActiveNames = formHooks.useSelector(
  selectActiveItems,
  items => items.map(item => item.name)
);

selectActiveCount(formState.data)  // number
selectActiveNames(formState.data)  // string[]

Selectors with multiple inputs

Pass multiple input selectors to combine values from different parts of the state. The result function receives each extracted value as a separate, typed argument.

tsx
const schema = z.strictObject({
  orders: z.array(
    z.object({
      product: z.formString(),
      quantity: z.formNumber(),
      unitPrice: z.formNumber(),
      shipped: z.formBoolean(),
    })
  ),
  discountPct: z.formNumber(),
});

const { formState, formHooks } = useFormState(schema);

// Select unshipped orders
const selectPendingOrders = formHooks.useSelector(
  state => state.orders,
  orders => orders.filter(order => !order.shipped)
);

// Combine the filtered list with the discount to compute an order summary
const selectOrderSummary = formHooks.useSelector(
  [selectPendingOrders, state => state.discountPct], // array of selectors
  (pending, discountPct) => {
    const subtotal = pending.reduce((sum, o) => sum + o.quantity * o.unitPrice, 0);
    const discount = typeof discountPct === 'number' ? discountPct / 100 : 0;
    return {
      count: pending.length,
      subtotal,
      total: subtotal * (1 - discount),
    };
  }
);

const summary = selectOrderSummary(formState.data);
// { count: number; subtotal: number; total: number }

selectOrderSummary only recomputes when either pending (the output of selectPendingOrders) or discountPct changes — not on every render.

The useSelector API is intentionally compatible with reselect — selectors written here can be swapped for reselect selectors and vice versa.

Selecting by group

Pass a group name as the first argument to select that group's data slice. With no second argument the selector returns the group's data fields; with a second selector, it runs over the group's data — scoped so fields outside the group are a compile error. The result is memoized like any other selector.

typescript
// Whole data slice for the 'contact' group
const selectContact = formHooks.useSelector('contact');
const contact = selectContact(formState.data);
// { email: string; phone: string }   (only the group's fields)

// Scoped selector — input is narrowed to the group's data
const selectEmailDomain = formHooks.useSelector('contact', (data) =>
  data.email.split('@')[1]
);
const domain = selectEmailDomain(formState.data);

// Group slice as the data source
const domainFromSlice = selectEmailDomain(formState.getGroup('contact').data);

// formHooks.useSelector('contact', (data) => data.age)
//   ^ compile error: 'age' is not in the 'contact' group

State Listener (useListener)

Subscribe to form state changes from inside a component without triggering extra re-renders.

typescript
import { type StateChangeListener } from 'form-state';

const listener: StateChangeListener<FormSchema> = ({ type, data }) => {
  console.info(type, data);
};

function AppForm() {
  formHooks.useListener(listener);
  // ...
}

The event object:

Property Type Description
type 'change' | 'submit' | 'asyncValidating' | 'asyncValidated' What triggered the event. The async pair fires once per active async refinement around each validation pass — one asyncValidating and one asyncValidated per check.
data T Form data snapshot. For change-driven async events: asyncValidating carries the pre-change state (so listeners can read the value being replaced), and asyncValidated carries the post-change state with the freshly resolved async errors applied.
formData FormData? Native FormData — only on submit events.
submitCount number How many times the form has been submitted.
errors Record<string, string> Current error map.
triggerField string | undefined Async events only. Dot-notation path of the field whose change started the pass (e.g. 'name', 'users.0.email'). undefined for programmatic validateAsync() and other non-change triggers.
schemaPath string Async events only. Dot-notation path of the async refinement that fired this event. Property-level checks report the field path (e.g. 'username', 'users.0.email'); top-level checks attached to the root object report an empty string ''. When a schema declares multiple async checks, each active check produces its own asyncValidating / asyncValidated pair with the matching schemaPath.

Use the async events to drive a loading indicator next to a field while a server-side check is in flight — for example, a username uniqueness lookup that hits an API. The event pair is debounced for you: only one asyncValidating fires per burst of overlapping passes, so the indicator doesn't flicker while the user keeps typing. Checks gated by skipWhen or submitOnly are filtered out of this fanout, so listeners only see events for the refinements that actually ran.

typescript
import { useState } from 'react';
import { type StateChangeListener } from 'form-state';

function UsernameForm() {
  const [validatingField, setValidatingField] = useState<string | null>(null);

  const listener: StateChangeListener<FormSchema> = (event) => {
    // `schemaPath` identifies which async refinement fired — match by the
    // refinement's attachment path so multiple async checks don't interfere.
    if (event.type === 'asyncValidating' && event.schemaPath === 'username') {
      setValidatingField('username');
    } else if (event.type === 'asyncValidated' && event.schemaPath === 'username') {
      setValidatingField(null);
    }
  };

  const { formHooks, formActions } = useFormState(schema);
  formHooks.useListener(listener);

  return (
    <label>
      Username
      <input
        name={formActions.inferName('username')}
        onChange={(e) => formActions.change('username', e.target.value)}
      />
      {validatingField === 'username' && <span>Checking availability…</span>}
    </label>
  );
}

Field Watch (useWatch)

formHooks.useWatch(name, compute?) observes the raw DOM value of a named input as the user types — without needing a controlled value prop. It subscribes via useSyncExternalStore, bypassing React's normal render cycle so high-frequency reads don't trigger re-renders in unrelated components. Requires watch: true in the hook options.

This is the signal pattern applied to form fields: fine-grained subscriptions where only the components that read a value re-render — the same model Solid signals and Preact signals use to isolate updates from the surrounding tree.

typescript
// Enable watching at the hook / formConnect level
useFormState(schema, { watch: true });
// or: formConnect({ schema, watch: true })(MyForm)

// Watch a field by its inferName value, with an optional transform
const idValue = formHooks.useWatch(
  formActions.inferName((path) => path.id),
  (value) => value.trim()
);

// Use the live value to drive conditional rendering
{/^666(-\d*)?$/.test(idValue) && <DevilIcon />}

// Watch with a more complex transform — only keep valid values
const cleanId = formHooks.useWatch(
  formActions.inferName((path) => path.id),
  (val) => (/^\d+$|^(\d+-\d+)$/.test(val) ? val : '')
);
Note

useWatch reads the uncontrolled DOM value — it's most useful for inputs where you want to react to intermediate keystrokes without updating form state on every character, such as driving a live preview or badge next to the field.

Navigation Blocker (useBlocker)

A user fills out half a form, then clicks a link or hits the back button — and their edits are gone. formHooks.useBlocker lets you catch that moment and ask "are you sure?" before the navigation goes through.

The API is loosely based on React Router's useBlocker: it returns the same proceed() / reset() controls and a blocked state you check before confirming. The difference is that FormState's version is router-agnostic, so instead of receiving the route being navigated to, your function receives the form's own state and status — making "block while the form has unsaved changes" a one-liner:

tsx
const { blockerState, guard, proceed, reset } = formHooks.useBlocker(
  (state, status) => status.dirty
);

This guards navigation in two places:

  • Leaving the page entirely (closing the tab or reloading) is handled for you — the browser's native "leave site?" prompt appears automatically whenever your function returns true. Nothing else to wire up.
  • Moving around inside your app is up to you, because FormState doesn't know which router you use. Route your navigation through guard instead of calling it directly. If it's safe to leave, the navigation happens immediately; if not, it's held and blockerState flips to 'blocked' so you can show a confirmation. From there, proceed() lets the navigation through and reset() cancels it.
tsx
import { useFormState } from 'form-state';
import { navigate } from 'router'; // whichever React router you use

const { formHooks } = useFormState(schema, { initialData });
const { blockerState, guard, proceed, reset } = formHooks.useBlocker(
  (state, status) => status.dirty
);

// Instead of navigating directly, go through the guard:
<button onClick={() => guard(() => navigate('/next'))}>Next</button>

// When a navigation is held, show your own confirmation UI:
{blockerState === 'blocked' && (
  <div role="alertdialog">
    <p>You have unsaved changes. Leave anyway?</p>
    <button onClick={proceed}>Leave</button>
    <button onClick={reset}>Stay</button>
  </div>
)}

Because guard accepts any () => void callback, it isn't tied to a router at all — you can drive the browser History API directly. Route every pushState through the guard, and intercept the back / forward buttons via popstate:

tsx
import { useEffect } from 'react';
import { useFormState } from 'form-state';

const { formHooks } = useFormState(schema, { initialData });
const { blockerState, guard, proceed, reset } = formHooks.useBlocker(
  (state, status) => status.dirty
);

// Forward navigation: push through the guard instead of calling history directly.
const go = (url: string) => guard(() => history.pushState({}, '', url));

// Back / forward buttons: re-push the current URL, then guard the real move.
useEffect(() => {
  const onPopState = () => {
    history.pushState({}, '', location.href); // undo the browser's move first
    guard(() => history.back());              // then ask before actually leaving
  };
  window.addEventListener('popstate', onPopState);
  return () => window.removeEventListener('popstate', onPopState);
}, [guard]);

<button onClick={() => go('/next')}>Next</button>
{blockerState === 'blocked' && (
  <Confirm onYes={proceed} onNo={reset} />
)}

The confirmation dialog is entirely yours — FormState only tells you when to show it, never how. If you'd rather skip the browser's native prompt (which covers closing the tab and reloading the page) and only guard in-app navigation, pass { enableBeforeUnload: false } as the second argument.

useBlocker is router-agnostic by design — it never ties FormState to a particular router, which is why your function receives the form's state and status rather than the route being navigated to. To block a specific route, do the check inside shouldBlock and send your router's navigation through guard.

TanStack Query Integration

A common pattern is to fetch a record from the server, seed it into a form, let the user make changes, and save via a mutation. TanStack Query's useSuspenseQuery and useMutation compose cleanly with useFormState — query data flows into initialData, and mutateAsync fits naturally inside the handleSubmit callback.

bash
npm install @tanstack/react-query

Complete example

tsx
import { useSuspenseQuery, useMutation, useQueryClient } from '@tanstack/react-query';
import { useFormState, parseState, z, type SchemaDataObject, type SubmitState } from 'form-state';

const profileSchema = z.strictObject({
  name:        z.formString({ required: true }).with(z.describe('Name')),
  email:       z.formString({ required: true }).with(z.describe('Email')),
  dateOfBirth: z.formDate({ dateFormat: 'MM/dd/yyyy' }).with(z.describe('Date of Birth')),
  bio:         z.formString().with(z.describe('Bio')),
});

// Inferred form state shape TypeScript type
type ProfileData = z.infer<typeof profileSchema>;

// Derived API type — empty literals replaced with `undefined`, optional fields use `?`
type ProfileApiData = SchemaDataObject<ProfileData>;

// Your fetch layer — swap for any HTTP client
declare const api: {
  getProfile(userId: string): Promise<ProfileApiData>;
  updateProfile(userId: string, values: ProfileApiData): Promise<void>;
};

function FormError({ error }: { error?: string }) {
  return error ? <span className="field-error">{error}</span> : null;
}

function ProfileForm({ userId }: { userId: string }) {
  const queryClient = useQueryClient();

  // 1. Fetch and validate current server data
  const { data } = useSuspenseQuery({
    queryKey: ['profile', userId],
    queryFn: async () => {
      const apiData = await api.getProfile(userId);

      // Validate the API response against the schema.
      const result = parseState(profileSchema, apiData);

      if (result.success) {
        return result.data;
      } else {
        throw new Error(result.errors.getAll().join(' | '));
      }
    },
  });

  // 2. Seed the form with the loaded server data
  const { Form, formState, formStatus, formActions, formHandlers } =
    useFormState(profileSchema, {
      initialData: data,
    });

  // 3. Mutation for saving
  const { mutateAsync } = useMutation({
    mutationFn: (values: ProfileApiData) => api.updateProfile(userId, values),
  });

  // 4. Submit handler — mutateAsync lives inside the async callback
  const handleSubmit = formHandlers.handleSubmit(
    async (submitState: SubmitState<typeof profileSchema>) => {
      if (!submitState.valid) {
        return submitState.errors;
      }

      try {
        await mutateAsync(profileSchema.toObject(submitState.data));
        return true;
      } catch (err) {
        return { serverError: err instanceof Error ? err.message : 'Save failed.' };
      }
    },
    {
      onSuccess: () => {
        queryClient.invalidateQueries({ queryKey: ['profile', userId] });
      },
    }
  );

  return (
    <Form action={handleSubmit}>
      <FormError error={formState.errors.getManual('serverError')} />

      <label>
        {formState.descriptions.name}
        {formState.required.name && <span> *</span>}
        <input
          value={formState.data.name}
          required={formState.required.name}
          onChange={(e) => formActions.change('name', e.target.value)}
          onBlur={() => formActions.touch('name')}
        />
        <FormError error={formState.errors.name} />
      </label>

      <label>
        {formState.descriptions.email}
        {formState.required.email && <span> *</span>}
        <input
          type="email"
          value={formState.data.email}
          required={formState.required.email}
          onChange={(e) => formActions.change('email', e.target.value)}
          onBlur={() => formActions.touch('email')}
        />
        <FormError error={formState.errors.email} />
      </label>

      <label>
        {formState.descriptions.dateOfBirth}
        <input
          type="text"
          placeholder={formState.patterns.dateOfBirth}
          value={formState.data.dateOfBirth}
          onChange={(e) => formActions.change('dateOfBirth', e.target.value)}
          onBlur={() => formActions.touch('dateOfBirth')}
        />
        <FormError error={formState.errors.dateOfBirth} />
      </label>

      <label>
        {formState.descriptions.bio}
        <textarea
          value={formState.data.bio ?? ''}
          onChange={(e) => formActions.change('bio', e.target.value)}
          onBlur={() => formActions.touch('bio')}
        />
      </label>

      <button type="submit" disabled={formStatus.submitting}>Save Changes</button>
    </Form>
  );
}

    <ErrorBoundary fallback={<ErrorMessage />}>

Seeding initialData from a query

With useSuspenseQuery, data is always defined — the component suspends until the query resolves, so useFormState always receives the full server value on first render.

tsx
const { data } = useSuspenseQuery({
  queryKey: ['profile', userId],
  queryFn:  () => api.getProfile(userId),
});

// data is always ProfileData here — the component suspends until resolved
useFormState(profileSchema, { initialData: data });
Dirty-field protection

initialData only updates non-dirty fields. Once a user edits a field it is marked dirty and subsequent query revalidations will not overwrite their input. Background refetches and cache invalidations are therefore safe — they sync server-computed fields without clobbering in-progress edits.

Validating fetched data against the schema

Use parseState inside queryFn to validate the API response before it reaches the form. If validation fails, the thrown error bubbles to the nearest <ErrorBoundary> — no form state is ever touched.

tsx
import { parseState } from 'form-state';

const { data } = useSuspenseQuery({
  queryKey: ['profile', userId],
  queryFn: async () => {
    const apiData = await api.getProfile(userId);
    const result = parseState(profileSchema, apiData);

    if (result.success) {
      return result.data;
    } else {
      throw new Error(result.errors.getAll().join(' | '));
    }
  },
});

Handling loading and errors

Because useSuspenseQuery suspends while loading and throws on error, both states are handled outside the component by wrapping it with <Suspense> and an <ErrorBoundary>:

tsx
<ErrorBoundary fallback={<ErrorMessage />}>
  <Suspense fallback={<Skeleton />}>
    <ProfileForm userId={userId} />
  </Suspense>
</ErrorBoundary>

Inside ProfileForm, data is always defined — no isPending or isError guards needed.

Note

If you prefer conditional rendering over Suspense and ErrorBoundary, swap useSuspenseQuery for useQuery and handle isPending and isError directly inside the component.

    if (!submitState.valid) return submitState.errors;

    try {
      await mutateAsync(profileSchema.toObject(submitState.data));
      return true;                         // signals success to formStatus
    } catch (err) {
      // Returning an object surfaces it as a manual error in the form
      return { serverError: err instanceof Error ? err.message : 'Save failed.' };
    }
  }
);

Invalidating the cache after a save

Use the onSuccess option to invalidate the query after a successful submission. This triggers a background refetch so any server-computed fields — updated timestamps, derived values, server-assigned IDs — flow back into the form via initialData.

tsx
const handleSubmit = formHandlers.handleSubmit(
  async (submitState) => { /* ... */ },
  {
    resetDirty: true,
    onSuccess: () => {
      // Refetch fires in the background; dirty-field protection means the
      // fresh data fills only fields the user hasn't touched since the save.
      queryClient.invalidateQueries({ queryKey: ['profile', userId] });
    },
  }
);

Surfacing server errors in the form

When the mutation throws, return an error object from the submit callback. Any key prefixed with _ is treated as a form-level error; other keys are matched against field paths.

tsx
// Form-level error — display it near the submit button or at the top
return { serverError: 'The server is unavailable. Try again later.' };

// Field-level error returned from the server
return { email: 'This email is already registered.' };

// Read either with getManual() — schema errors use errors.name, errors.email etc.
<FormError error={formState.errors.getManual('serverError')} />
Note

Manual errors set via a returned object are cleared automatically when the user next edits the affected field. formStatus.valid is false while any manual error is present; see the Manual Errors section for the full API.

Tools

DevTools

The form-state-tools package provides FormDock — a development-only floating panel that gives you a live view of your form's internal state, validation status, and captured runtime errors. It renders nothing in production (NODE_ENV=production).

bash
npm install github:dstarosta/FormStateTools#v1.0.0

Setup

Pass the entire return value of useFormState (or useFormStateContext) to the form prop. Drop it anywhere in your component tree — it positions itself as a fixed bottom dock.

tsx
import { FormDock } from 'form-state-tools';

function AppForm() {
  const form = useFormState(schema);   // or useFormStateContext(schema)
  const { Form, formHandlers } = form;

  return (
    <>
      <Form action={formHandlers.handleSubmit(onSubmit)}>
        {/* ... */}
      </Form>

      <FormDock form={form} />
    </>
  );
}
Tip

For projects with SSR, such as Remix or TanStack Start, NODE_ENV may not be set to development automatically. Without it, FormDock may render on the server and break SSR. Pass your build's dev flag to devMode to be explicit:

tsx
<FormDock form={form} devMode={isDev} />

In Vite, isDev would be import.meta.env.DEV; in Webpack it might be process.env.NODE_ENV !== 'production'.

Vite plugin (auto-inject)

If you use Vite, the form-state-tools/vite plugin can mount the dock for you — no <FormDock> in your JSX. Add it to your Vite config and feed it your form state with the useFormDock hook. The plugin auto-detects how to inject the dock: it uses the HTML entry for plain Vite/React SPAs, the framework client entry for TanStack Start, and the root module (root.tsx) for React Router 7 (Remix).

Vite only

This plugin is a Vite plugin — it does nothing under other bundlers. On Next.js, Create React App, or any non-Vite setup, skip the plugin and use the manual <FormDock form={form} /> setup above, which works in any React app.

ts
// vite.config.ts
import { defineConfig } from 'vite';
import formStateTools from 'form-state-tools/vite';

export default defineConfig({
  plugins: [
    formStateTools(),
    // ...your other plugins
  ],
});

Then call useFormDock in your form, passing the same value you would pass to the form prop. The dock the plugin injects subscribes to whatever you report:

tsx
import { useFormDock } from 'form-state-tools';

function AppForm() {
  const form = useFormState(schema);   // or useFormStateContext(schema)
  const { Form, formHandlers } = form;

  useFormDock(form);   // feeds the plugin-injected dock — no <FormDock> needed

  return (
    <Form action={formHandlers.handleSubmit(onSubmit)}>
      {/* ... */}
    </Form>
  );
}
The plugin is not part of your bundle

formStateTools() only applies during vite dev (apply: 'serve'), so it — and the dock it injects — are never included in your production build. The plugin code itself runs in Node at dev time, not in the browser, so it adds nothing to your shipped JavaScript. In a production build, useFormDock is a no-op that tree-shakes away.

Tip

For an SSR framework whose client entry is not auto-detected, point the plugin at your client-entry module with the clientEntry option — a substring matched against module ids (e.g. formStateTools({ clientEntry: 'entry-client' })). This must name a JavaScript module, not an HTML file. When set, the dock is mounted only from that module.

You do not need it for SPAs, TanStack Start, or React Router 7 (Remix) — all are auto-detected.

Plugin options

Pass an options object to formStateTools() to control where the dock is injected and how it behaves. Every option is optional; omit them to accept the defaults.

ts
formStateTools({
  collapsed: false,
  captureErrors: 'console',
  ignoreErrorPatterns: [/ResizeObserver/, 'Network request failed'],
})
Option Type Default Description
enabled boolean dev only Overrides the automatic dev-only behavior. Set true to inject the dock even in non-dev builds, or false to turn the plugin off entirely.
clientEntry string auto-detected A substring matched against module ids to locate your app's client-entry module. Only needed for SSR setups whose client entry is not auto-detected. Must name a JavaScript module, not an HTML file.
collapsed boolean true Whether the dock starts in its collapsed state.
captureErrors 'all' | 'console' | 'thrown' | 'none' 'all' Which kinds of errors the dock surfaces as an on-screen toast: thrown errors, console.error calls, both, or none.
ignoreErrorPatterns (string | RegExp)[] [] Patterns for errors the dock should not show. An error is ignored when its message matches any of these patterns. RegExp patterns keep their flags.

Configuration examples

tsx
// Start expanded, only capture console.error calls
<FormDock form={form} collapsed={false} captureErrors="console" />

// Suppress noisy third-party errors
<FormDock
  form={form}
  ignoreErrorPatterns={[
    /ResizeObserver loop/,
    'Non-Error promise rejection',
  ]}
/>

// Force-disable in dev for a specific story/test
<FormDock form={form} devMode={false} />
Tip

FormDock saves the last-used panel size to sessionStorage so it persists across hot reloads. The collapsed prop is only used when there is no saved size.

Production safety

When NODE_ENV=production, FormDock returns null immediately. No panel markup, no error listeners, no bundle overhead beyond the conditional check.
